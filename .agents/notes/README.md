# Agent Notes

Agent Note 记录需要长期保留的架构决定，回答“为什么这样设计”。它不替代当前态文档、功能文档或 PR 描述，也不记录普通工作流水账。

## 何时使用

满足以下任一情况时，可以创建 Agent Note：

- 改动跨越多个生产目录，重新划分模块职责或依赖边界。
- 改变 package 导入、patch、extension、override 或注册机制的生效顺序。
- 改变公共配置、checkpoint、模型兼容性或长期测试边界。
- 方案需要多个 PR 分阶段完成，合入后仍有明确的迁移债务和退出条件。
- 存在多个合理方案，需要保留选择依据，避免后续重复讨论。

设计已经确定并开始实施时，Agent Note 随第一个实现 PR 提交。纯头脑风暴和没有实施计划的提案保留在本地。

以下改动不创建 Agent Note：

- 普通新功能、Bug 修复、单文件重构和测试补充。
- 遵循现有规则的机械搬迁、重命名或 import 更新。
- 临时排障、命令记录、测试日志和运行结果。
- 已能由代码、当前态文档和 PR 描述完整说明的局部改动。

同一架构决定只维护一份 Note。后续 PR 更新原 Note 的状态、阶段和验证结果，不重复创建文件。

## 状态与目录

仓库使用两个活跃状态：

- `proposed/architecture/`：未完成或分阶段实施的提案，可写目标目录、迁移步骤、验收条件和风险。
- `implemented/architecture/`：已完整落地的决定，只描述当前机制、取舍和持续验证。

提案完成后精简并移动到 `implemented/`。如果决定已经被正式文档完整吸收，不再提供额外的设计依据，则删除 Note。被放弃、长期未推进或被其他方案替代的 Note 应删除；只有拒绝原因仍具有长期价值时才归档。

## 内容要求

文件名为 `YYYY-MM-DD-topic.md`，并包含 `Status`、`Created`、`Last updated` 和关联 Issue/PR。

所有 Note 必须包含：

- `Context`：问题、背景和需要长期保留的约束。
- `Proposal` 或 `Decision`：计划采用的方案或最终决定。
- `Consequences`：兼容性、长期约束和后续影响。

以下章节按实际需要添加，不能为了满足模板填充空泛内容：

- `Alternatives considered`：存在需要保留的重要备选方案时。
- `Acceptance criteria`：分阶段实施或需要明确完成边界时。
- `Risks`：存在显著兼容性、数值、性能或维护风险时。
- `Migration plan`：需要多个 PR 或跨版本迁移时。

完成后将 `Proposal` 改为 `Decision`，保留仍有价值的背景、方案取舍和影响；删除临时任务清单、过期路径、阶段日志和已经失效的验证计划。架构阶段合入时，同步更新代码、相关 `AGENTS.md`、当前态文档和本 Note。

## 体量与清理

- 一个文件只记录一个架构决定。
- 单个 Note 建议不超过 200 行或 20 KiB；超过时拆分独立决定。
- 不粘贴完整代码、长日志、聊天记录、本机路径、环境名称或临时资源信息。
- 测试只记录结论和必要命令；大段证据保存在 CI、Issue 或其他产物中。
- `proposed/` 中超过 90 天未更新的 Note 必须复核，选择继续更新、转为 implemented 或删除。

判断标准：如果未来开发者需要理解“为什么这样设计”，并且答案不能只靠代码、当前态文档和 PR 描述获得，就使用 Agent Note。
